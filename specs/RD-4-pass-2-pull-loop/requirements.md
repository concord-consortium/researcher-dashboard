## Overview

Turn the spike's runner into the pull-model runner of `final-design.md`: it stops being dispatched to, asks report-service for its work (`POST /work`), its storage credentials (`POST /storage-credentials`) and its suspend (`POST /idle`), and makes no AWS call on the Lambda execution role. Every per-package path, the archive key, the result document and the cc-data dataset are keyed by the package's identity and catalog id; applicability is asked of report-server and enforced by the runner; the package is handed `scope.json` and writes `display.md` and `summary.txt`; the result becomes one document per researcher per package per class, with the counts on the researcher's own scope document; the lifecycle hooks follow `final-design.md` 7.1 and 7.2; `POST /refresh-token` and the dispatch route are deleted; section 3's renames land; the image's cc-data moves to the pre-release carrying the package commands; and a smoke script gates the image.

## Project Owner Overview

Today the researcher's machine waits to be told what to run, and it reads and writes student data with one shared AWS permission that reaches every researcher's data. After this pass the machine wakes, asks for its own work, runs it, and asks to be put back to sleep, and every byte it stores or fetches goes through short-lived credentials that reach only its own researcher's folder and the published packages. RD-1's runner stack is built without the shared permission, so this runner is the first that can work on it at all.

Researchers see the difference as behavior that used to break: a machine that slept for two hours now wakes and runs the work waiting for it, each researcher's results and counts are their own, a package that does not suit a class is refused even if something offered it, and two packages with the same name from different authors no longer collide. It is also the runner the first real package (Wildfire's open responses, REPORT-147) runs on. Nothing changes on the page until RD-3 builds the new app, which renders what this runner writes.

**What the runner on `main` does** (read in full, `49df5d2`):

- `server/index.js` serves Lambda's five hooks under `/aws/lambda-microvms/runtime/v1/` (`ready`, `run`, `resume`, `suspend`, `terminate`) and three routes of its own: `POST /run-package` (the spike's dispatch), `POST /refresh-token` (no caller anywhere) and `GET /`. `buildRunner` picks S3 or DIR backends and a Firestore, memory or log status store.
- `server/runner.js` `run()` parses `runHookPayload`, starts the egress proxy and network namespace, verifies the sandbox, signs in with the session token, writes `starting`, builds the syncer with `new S3Backend({bucket, prefix})` on the default chain, pulls the researcher's prefix down, logs cc-data in with the report-server token, starts the syncer's 30-second timer and writes `ready`. `startPackage()` takes `{scope: {kind, class_hash, class_id}, package: {name, version, checksum}, class_tokens}`, refuses a name with `/`, checks the class tokens' claims, fetches the package (`resolvePackage`), checks the declared duration against an eight-hour window from `/run`, signs a class store in once per class for the VM's life (`#classStores`), writes the shared result `classes/{class_hash}/results/{name}` with `requested_by`, runs `pullData` (the CLUE read when `required_inputs` includes `clue_documents`), `preparePackage`, a write probe and `runPackage` under a 30-minute `setTimeout` race, then writes `data` onto the shared `classes/{class_hash}` document and the result `done` with `display.json`'s structure. `resume()` writes `ready` and restarts the syncer; `suspend()` flushes and verifies; `terminate()` fails a running result with "VM terminated during analysis", revokes the report-server token, flushes and writes `terminated`; `refreshToken()` checks the new token's `platform_user_id` and re-signs in. Every status write awaits Firestore with no timeout.
- `server/status.js` writes `researcher_dashboard/{portal}/researchers/{platform_user_id}` (the session document) and the class and result documents with ISO-string timestamps.
- `server/steps.js` holds `CLUE_PROJECT = "collaborative-learning-staging"` and looks the CLUE class token up by that key; `server/firebase-projects.js` knows only the two staging projects, though its comment already records that CLUE production is row `collaborative-learning` for project `collaborative-learning-ec215`.
- `server/package-env.js` keys the package's home and output directory by name, names the dataset `<portal host>/<name>`, and hands the package `RD_CLASS_HASH`, `RD_PORTAL_CLASS_ID`, `RD_DATA_DIR`, `RD_OUTPUT_DIR`, `RD_DATASET`, `CC_DATA_ROOT`, `CC_DATA_LOCAL`, `CC_DATA_PORTAL`, `RD_REPORT_SERVER_URL`, `RD_BUCKET`, `RD_STORAGE_PREFIX` and the proxy variables. It reads `counts.json` (`answers`, `learners`, `logs`, `log_freshness_at`) back from the output directory.
- `server/package-fetch.js` fetches `<name>/<version>.zip` into `<workRoot>/packages/<name>/<version>.zip`, verifies the checksum, unzips with the image's `unzip` (no bound on what it writes) and checks the manifest's name and version.
- `server/sync/` pushes changed files on a 30-second `setInterval` and flushes and verifies for the hooks. `S3Backend` is `new S3Client({})`.
- The image (`Dockerfile`) creates the `analysis` user (uid 1000) and `/work` owned by it; `netns.js` names the namespace `analysis`; `config.js` reads `ANALYSIS_UID` and `ANALYSIS_TIMEOUT_MS`. The stack's image passes only `PORT`, `DATA_ROOT`, `SYNC_BACKEND` and `STATUS_BACKEND` (RD-1's `MicrovmImage`), so none of those renamed variables is set by the stack.
- `npm test` passes 137 tests on Node 24.14 (2026-10-08, run on a scratch copy with `node_modules` symlinked from the main checkout; nvm's Node 24 is not on a non-interactive shell's `PATH`).

**What REPORT-143 builds for this runner** (merged on report-service `master` as `bfbda61`, PR #438, its spec closed as `specs/REPORT-143-vm-endpoints-and-watchdog.md`, whose Technical Notes paragraph "The runner's side of the lease (RD-4 pass 2)" is this runner's hand-off; contracts also in `speccing.md`, "REPORT-143's contracts for later stories"):

- `POST /work`, `/idle` and `/storage-credentials` on the `researcherDashboard` function (`function_url` in `runHookPayload`). Each takes the VM's Firebase **ID token** for report-service's project as `Authorization: Bearer`, 401 without or unverifiable, 403 without `researcher_dashboard_runner === true`, `user_type: "researcher"`, a positive-integer `platform_user_id` and an `http(s)` `platform_id`. Errors are `{success: false, error}` (`functions/src/middleware/response-methods.ts`).
- `/work`, body `{microvm_id}`: 400 without it, 409 unless it is the recorded VM (the launch is recorded one transaction after `RunMicrovm` returns, so a 409 right after boot is expected and retried for up to a minute). 200 `{success: true, packages: [{class_hash, package_key, identity, version, checksum, catalog_id}], scopes: {<class_hash>: {scope, class_tokens}}, session_token, firebase_project}`. Only entries whose result says `queued` (or has no result), in queue order; idempotent; removes nothing. The session token and `class_tokens[firebase_project]` are freshly minted by the function on every call for the recorded VM within eight hours of its launch, together under a 10-second bound, a mint that fails or overruns answering 502; an empty queue still answers 200 with a fresh session token. CLUE's class token is passed through as rigse minted it, good for an hour from the request.
- `/idle`, body `{microvm_id}`: with work queued, 200 `{success: true, suspended: false, work_queued: true}`; with a `running` result naming this VM, 200 `{success: true, suspended: false, run_in_progress: true}` (REPORT-143 R10), which this runner, never asking mid-run, gets only through a bug or a run whose final write was lost; otherwise `SuspendMicrovm` on the recorded VM and 200 `{success: true, suspended: true}`; 409 for another VM; 502 if the suspend fails. It writes nothing, and its answer can reach a VM that is already suspending.
- A runner session is bounded by its first sign-in (REPORT-143 R3a): tokens `/work` mints carry `runner_signed_in_at`, and the routes and the rules refuse a session that signed in more than 8 hours 10 minutes ago, or more than a minute before the recorded launch. The runner signs in during `/run` and with each `/work` answer, which passes unchanged (#264, #265).
- `/storage-credentials`, no body: 200 `{success: true, access_key_id, secret_access_key, session_token, expiration (ISO 8601), bucket, prefix: "researchers/<id>/", region: "us-east-1"}`, one hour, under the session policy recorded in `speccing.md` ("The storage broker's contract for REPORT-143"): list and read-write under `researchers/<id>/`, `GetObject` on `packages/*`, nothing else. No list on `packages/`, so a missing archive answers `AccessDenied`, not `NoSuchKey` (RD-1, Technical Notes). Keyless means the function holds no AWS key: it assumes the broker role with `AssumeRoleWithWebIdentity` on a Google ID token it mints per call. The runner still receives explicit STS credentials in the same body. The function answers 503 naming an empty `RD_BROKER_ROLE_ARN`, `RD_DATA_BUCKET` or `RD_AWS_AUDIENCE`, and 502 for a mint failure, an STS refusal or more than 10 seconds.
- The rules (REPORT-143 R22, R22a, `firestore.rules` on `master`): `runners/{uid}` is written only by a runner token for that researcher, with `platform_id` equal to the token's and the stored one's, and `updated_at == request.time`; `classes/{h}/researchers/{uid}` and its `results/{key}` only by a runner token carrying that `class_hash`, so the session token cannot write them; every result write sets `updated_at` to server time, and a write that sets or changes `started_at` sets it to server time, while none may clear it; a result written `running` carries `expected_duration_seconds` (an integer 1 to 28,800), `microvm_id` (a string) and `heartbeat_seconds` (an integer 30 to 120); nothing can be deleted; `classes/{h}` is readable by a researcher token for the class and written only by the function.
- The watchdog's lease (REPORT-143 R17, Q13): a `running` result is stale after 5 × `heartbeat_seconds` without an `updated_at`, counted from the later of `updated_at` and `vms/`'s `resumed_at` for the same VM. A stale result whose runner has moved on (the runner document names the same VM, is not in a terminal state, names another `current_package`, and was updated after the result) is failed with no kill; otherwise a gone or `TERMINATED` VM's result is failed, an awake VM is terminated and its result failed on a later pass, and a `SUSPENDED` VM is terminated only after the declared duration plus 10 minutes. Every such failure carries one reason, "The machine running it stopped before the run finished; run it again." A lost run on an awake VM reads failed about 7 to 9 minutes after its runner goes quiet. The idle sweep suspends an awake VM with nothing queued, no running result of its own and 30 minutes without activity; a suspended VM with queued work is resumed. A gone VM's runner document is written `terminated` with `current_package` cleared, only while its `microvm_id` is that VM and its state is not already terminal (R19a). The `microvm_id` comparisons are with `vms/`, which holds `RunMicrovm`'s id.
- `/run-package` writes a re-queued result whole with `previous`, the last finished run (REPORT-143 R8a); every other writer merges named fields, so `previous` survives them.

**What report-server adds for this runner** (REPORT-167, spec'd `c51f93e` on `REPORT-167-report-service-one-home-for`, unpushed, planned to merge before REPORT-143; `final-design.md` 5.5 and 10):

- **The only glob matcher.** `POST /api/v1/packages/applies` (`:api_authenticated`, so the runner's own report-server token, the `report_server_token` of `runHookPayload`, as `Authorization: Bearer`) takes `{urls: {all, any, none}, assignment_urls, scope_urls}`. `urls` is required (absent or `null` is 400; a `null` group is empty) and checked with publish's pattern rules. `scope_urls` is at most 1,000 strings of at most 2,048 **code points**, matched as given (code points since `c51f93e`, channel #42, so every URL the function keeps in a profile, which it bounds at 2,048 UTF-16 units, passes); `assignment_urls` are sent through report-service's deriver first, which can take up to 270 seconds (REPORT-167 R14, R15). It answers 200 `{applies, reason, interactive_urls, unread, truncated}`, `reason` `null` when it applies and otherwise one of the runner's three wordings: "no URL in this class matches the required pattern <p>", "no URL in this class matches any of <p1>, <p2>", "a URL in this class matches the excluded pattern <p>" (R7, R16). A bad body is 400 `BAD_REQUEST`, a failed derivation 503, and neither route ever answers 404 (R17). It writes nothing and takes no scope id (R18).
- **The contract fixture.** `fixtures/package-contract.json` at report-service's root holds `identity` (19 cases), `version` (14), `package_key` (2) and `limits: {max_duration_seconds: 7200, max_url_length: 2048}`; its `about` says "The runner and the dashboard app assert against it too" (REPORT-167 R26, its implementation spec). It is not in REPORT-167's spec commit: the cases exist in its throwaway build (branch oob `stage-verification/stage5-throwaway-build.patch`), and `limits` is added by the spec. The identity grammar tightens to `^(users|projects)/[1-9][0-9]{0,17}/[a-z0-9][a-z0-9-]{0,62}$`; the version grammar is REPORT-142's, `(0|[1-9][0-9]*)` per part with an optional prerelease and no `+build`, at most 64 characters.
- **The runner's stricter rules at publish.** report-server refuses a manifest declaring more than 7,200 seconds and an archive holding any symbolic-link entry (REPORT-167 R21, R22). Versions published before it are not re-checked, so the runner's own checks stay. **R26 of REPORT-167**: "the runner's ceiling is a setting (`PACKAGE_MAX_DURATION_SECONDS`, up to 28,800), so RD-4 asserts that its default equals `limits.max_duration_seconds` and refuses at startup a configured value below it, since a deploy that lowers it would refuse packages report-server accepts."

## Requirements

### The pull loop

- **R1.** `runHookPayload` must carry `function_url` beside the fields it carries today, and the runner reads its own MicroVM id from `/run`'s body as `microvmId`. `/run` fails (500, so Lambda destroys the VM) when either is missing, because `/work` and `/idle` refuse any call without the VM's own id, and a result cannot be written `running` without `microvm_id` (REPORT-143 R6a, R10, R22a). A VM that cannot take work is stopped at once rather than left awake until the watchdog or the eight-hour cap.
- **R2.** The runner calls `POST /work` with `{microvm_id}` as `/run` returns (started by it, never awaited by it, since `/run` has 60 seconds), after every resume, after every package finishes, and while idle (R10). The call authenticates with an ID token of the current session store, forced fresh after a resume (R20), and every call to the function is bounded at 15 seconds. A 409 in the first 60 seconds after `/run` is retried every 5 seconds; after that, and for any other failure, the runner waits one idle poll interval (R10) and tries again, logging each failure. `/work` is never called from inside a lifecycle hook.
- **R3.** Every `session_token` the runner is handed, at `/run` and in each `/work` answer, is used to sign in a new session store, and the runner reads that store's verified ID-token claims: `platform_user_id` must equal the payload's, `platform_id` the payload's, and `researcher_dashboard_runner` must be `true`. A token that fails the check is not adopted: at `/run` the hook fails; from `/work`, that answer is discarded, nothing it names is run, and the failure is logged. `firebase_project` in a `/work` answer must equal the payload's.
- **R4.** Stores are per request, never per VM. Each `/work` answer that is adopted gets its own session store and, for each class it names, its own class store, signed in with that answer's class token for `firebase_project` before the first write for that class. A store is never reused by a later request; the previous request's stores are deleted (`deleteApp`) once the new session is signed in, except a class store a running package is still writing through, which goes once that package's final write has settled (R44b).
- **R5.** A class token is used only if its store's verified claims name the payload's `platform_user_id` and `platform_id`, carry the runner claim, and carry the `class_hash` of the class it is keyed under. A class whose token fails, or whose `firebase_project` token is missing, has its handed-out packages skipped for that request, logged, and not claimed (its results cannot be written, R42).
- **R6.** For each adopted `/work` answer, the runner reads each class's scope block, validates it (`kind: "class"`, `id` equal to the class hash, `classes` a one-element list naming that hash and a positive integer `class_id`, `assignments` a list), and takes the packages in the order given. Any package whose identity, version, checksum or catalog id does not match the catalog grammar (identity `^(users|projects)/[1-9][0-9]{0,17}/[a-z0-9][a-z0-9-]{0,62}$`, version `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(-[0-9A-Za-z.-]+)?$` and at most 64 characters, checksum `^sha256:[0-9a-f]{64}$`, catalog id a positive integer) is failed with the reason (R43), not run. A test asserts the identity and version checks and the package key (R29) against every case of REPORT-167's `fixtures/package-contract.json`, which this repository holds as a byte-identical copy at its own `fixtures/package-contract.json`, kept in step by `runner/scripts/contract.mjs` (Q14): `npm run contract:sync` fetches report-service's file from GitHub (`master` by default, or `--ref`) and writes the copy, and `npm run contract:check` fails when the copy differs. The release (R58) and the monthly rebuild (R54) run `contract:check`.
- **R7.** **Claiming.** A package is claimed by writing its result `running` (R43). Before the claim, the runner has fetched and verified the archive (R30), read the manifest, applied the ceiling (R26) and the window (R25), and checked applicability (R34); a package refused at any of those is written `failed` directly, never `running`. One package runs at a time. After a package finishes, the runner calls `/work` again rather than continuing through the previous answer, so work appended meanwhile is seen, and each package's writes use tokens minted seconds before it started.
- **R8.** **The status document** `runners/{platform_user_id}` is written through the session store. On a claim: `state: "running"`, `current_package: {class_hash, package_key}`, and `queue` set to the answer's remaining queued entries as `{class_hash, package_key}` pairs, excluding the claimed one and any the same plan wrote `failed`. When `/work` hands out nothing: `state: "ready"`, `current_package: null`, `queue: []`, written once when the queue drains and not again on each idle poll while nothing changes; a package refused while the VM is drained is a change, so `ready` is written again to take it off the `queue` the function wrote on append. Every write carries `platform_id` and `updated_at` as server time (REPORT-143 R22a). The function also writes `queue` on append, so it may lag by one write (REPORT-143, "For RD-3"). **While a run is outstanding, every write to this document writes `current_package` naming that run**, the `/suspend` and `/terminate` hooks' included, taken from the run the runner holds, so a claim-time write that was lost is repaired by the next one rather than leaving the previous package or `null` behind; a hook with no run outstanding leaves the field alone. Only the next claim or the drained `ready` names something else, and both come after the run's final write has settled (R44b). That is what makes REPORT-143 R17's moved-on case safe: a document naming another package means this run will never be written again. The runner writes `microvm_id` exactly as `/run`'s body gives it, on this document and on every claim (R1, R43).
- **R9.** A claim write that is refused or fails leaves the package unclaimed. The runner does not claim it again in the same awake period after three attempts, logs `package.claim_failed` each time, and goes on with the rest, so a result it cannot write does not become a tight loop. A package it has stopped trying counts as nothing to do, so the idle loop (R10) runs, and since `/idle` then answers `work_queued`, the VM stays awake polling at 30 seconds until the entry is resolved or the VM reaches its cap. That is loud in the log and costs no more than an idle VM. The count is for one awake period and one queued run: it is cleared when the runner writes the entry's result (`running`, `done` or `failed`) and on every resume, so a package run again starts with three attempts (REPORT-143 re-appends a finished package).
- **R10.** **Idle.** When `/work` hands out nothing, the runner polls `/work` every 30 seconds (`IDLE_POLL_MS`) until 5 minutes (`IDLE_PERIOD_MS`) have passed since it last had work, then flushes and verifies the sync (R22's fallback, always on) and calls `POST /idle` with `{microvm_id}`. Both are code defaults with an environment override, not stack parameters. Five minutes is well under the watchdog's 30-minute idle sweep (REPORT-143 R18), and polling keeps a run requested on a warm idle VM from waiting for the idle period, since `/run-package` does nothing to a running VM (REPORT-141).
- **R11.** `/idle` answering `work_queued: true` sends the runner straight to `/work`. `suspended: true` ends the idle loop: the `/suspend` hook follows. An answer with neither (`run_in_progress: true`, or anything else) is logged as `idle.declined` with the answer, and the idle period starts again, as after a failed call, so the runner does not call `/work` and `/idle` back to back with no sleep for as long as the function declines (landing tracker 3.2a). A 409 or 502 is logged and the runner returns to polling. A flush that does not verify skips the `/idle` call for that period, since a suspend without a proven flush is what `/suspend` exists to prevent.
- **R12.** **The `/idle` race.** Each resume starts a new epoch in memory. An answer or error from a call started in an earlier epoch is ignored, so a slow `/idle` answer that arrives after the VM has been suspended and resumed is not read as a failure or as permission to do anything (REPORT-143 R10, R11). A loop from an earlier epoch makes no further call either, so a pre-`/idle` flush that ends after a resume does not call `/idle`, which would suspend the VM under the new loop's running package.
- **R13.** The runner never lets the queue or a token reach a browser: it writes package keys and class hashes to documents the researcher already reads, and nothing else from `/work`.

### Storage credentials and the default chain

- **R14.** Every S3 client the runner builds is built from `/storage-credentials` credentials, with explicit `accessKeyId`, `secretAccessKey`, `sessionToken` and `region`, in one module, which refuses to build a client without all four. That covers the syncer's pushes, deletes and flushes, `/run`'s pull-down, and the package fetch. Nothing else in the runner imports an AWS SDK client.
- **R15.** The credentials are fetched with the current session store's ID token and checked against the wall clock immediately before each use: a credential within 5 minutes of its `expiration` is fetched again. Nothing refreshes them on a timer. A resume marks them stale (R20), so the first S3 call after a resume always fetches new ones whatever the VM's clock says. The response's `bucket` must equal the payload's and its `prefix` must be `researchers/<platform_user_id>/`, or the runner refuses to use it.
- **R16.** **The default chain is switched off in the runner's process** before anything else runs: `AWS_EC2_METADATA_DISABLED=true`, and every environment variable the SDK's default provider reads for credentials (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_PROFILE`, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, `AWS_CONTAINER_CREDENTIALS_FULL_URI`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_ROLE_ARN`) removed, with the shared credentials and config files pointed at `/dev/null`. So a default-chain client left anywhere fails with `CredentialsProviderError` at once, which names its cause, rather than with an `AccessDenied` from the execution role, which on RD-1's stack holds no S3. The switch is made when the process starts, which on a MicroVM is the image build before the snapshot, so each VM's `/run` reads its own environment and logs `aws.default_chain_disabled`, or `aws.default_chain_enabled` with the variables still set.
- **R17.** Tests: a source test that `new S3Client` appears in exactly one module and nowhere else in `server/`, and that no other `@aws-sdk/*` client is imported; a unit test that the builder refuses missing credentials; a test that a client it builds resolves exactly the broker's credentials while `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` hold sentinel values in the environment; a test that with R16 applied, `new S3Client({})` rejects `credentials()` with `CredentialsProviderError`; a test that `S3Backend` has no default client; and a test that `/run` in S3 mode fetches credentials, with the session's ID token, before its first S3 call.
- **R18.** A package archive that cannot be read is reported as "`packages/<identity>/<version>.zip` is missing or not readable", whether S3 answered `AccessDenied` or `NoSuchKey`, since without a list grant a missing key reads as `AccessDenied` (RD-1 pass 2, Technical Notes). Any other failure of the fetch, the storage broker's or the network's, is reported as "could not be fetched" with its own message, and logged with the error's name and message, since it is not the package's absence.
- **R19.** The syncer's interval does not start at `/run` until the credentials have been fetched and the pull-down has finished, and after a resume not until the post-resume `/work` has been adopted and credentials fetched (R20); `/suspend` stops it. While the VM is awake a tick uses the credentials like any other call, so one that finds them within R15's margin of their expiry fetches new ones.

### The lifecycle hooks

- **R20.** **`/resume` writes nothing.** It marks the session, class stores and storage credentials stale in memory, starts a new epoch (R12), and returns 200 at once. The post-resume cycle then runs outside the hook: an ID token forced fresh from the last session (bounded by a timeout), `/work`, adoption (R3, R4), credentials (R15), the syncer (R19), then the queue, once any package that was running when the VM was suspended has finished. The status document keeps whatever `/suspend` wrote until that cycle writes (`final-design.md` 7.1(a), 7.3).
- **R21.** **Every other hook's status write is bounded** at 10 seconds, catches its failure, logs `status.write_failed`, and records it in memory; the next successful status write carries the last ten recorded failures as `status_write_failures: [{hook, error}]`, each error redacted as result errors are (`log.js` `redact`), and clears them. Every runner-document write carries the field, empty when nothing is pending, so a reported failure leaves the document with the next write, and a failure recorded while a write is in flight waits for the one after. No hook returns non-200 because a status write failed. The failures that still fail a hook are the ones that should: `/run`'s payload, `microvmId`, token claims, sandbox verification, credential fetch and pull-down (R1, R3, R16); `/suspend`'s and `/terminate`'s flush verification (R22, R23).
- **R22.** **`/suspend`** writes `suspending` (bounded), stops the syncer's interval, flushes and verifies, and writes `suspended` (bounded) only when the flush is proven. Both writes keep `queue` by not writing it, and `current_package` as R8 says: the outstanding run's, written again, or left alone while idle. A flush that does not verify writes `failed` with the reason and returns 500, which is the deliberate exception (`final-design.md` 7.1(a)); the VM then stays awake, so the runner starts a new loop as after a resume, since the loop that asked `/idle` to suspend has ended. **The suspend-hook check** (REPORT-143 R1) is not answered yet: the spec assumes an API `SuspendMicrovm` delivers `/suspend`, and the runner flushes and verifies before every `/idle` (R10, R11) whatever the answer, so the data never depends on it. On a resume with no `/suspend` since the last activity the runner logs `lifecycle.resume_without_suspend`, which is the signal that the hook did not fire (Q5).
- **R23.** **`/terminate`**: if a package is running, its heartbeat is stopped (R44a) and its result is written `failed` with REPORT-143's one lost-VM reason, "The machine running it stopped before the run finished; run it again." (bounded, first, so it lands within the hook's 60 seconds whatever the flush costs); the report-server token is revoked (bounded at 10 seconds, a failure logged and ignored as today); the syncer flushes and verifies; the status document is written `terminated`, or `failed` with the incomplete-sync reason (bounded), **in a transaction that writes only while the document's `microvm_id` is this VM's**, so a VM the researcher launched within the hook's 60 seconds keeps its document; a document naming another VM is left alone and logged as `terminate.runner_doc_skipped`. The write names the outstanding run in `current_package` (R8). The hook's failure is the run's last word: a package that finishes or fails after it writes no counts and no final result, since what it left after the hook's flush was never synced. The flush's verification still fails the hook.
- **R24.** **`POST /refresh-token` and `POST /run-package` are deleted**, with their handlers, their tests, their mentions in comments, and the `refresh_token.*` and `analyze.*` log events. `GET /` stays for a human, reporting `state`, `microvm_id`, `current_package`, `expires_at` and the sync backend.

### The window, the ceiling and the timeout

- **R25.** **The window check runs twice.** Up front, for each adopted `/work` answer, once every package in it has been fetched and verified (R30): the declared durations of its packages are summed in order against the time left, which is the VM's eight hours from `/run` less 5 minutes for the last flush and the `/terminate` hook, and every package from the one the window runs out on is failed with "VM window exhausted: <n>s left, and this package and the ones before it declare <m>s". Then again before each claim: a package whose declared duration exceeds the time left is failed the same way, with the rest of that answer. Time left is read from the wall clock; whether the VM's clock advances across a suspend is not recorded, and the watchdog fails a run the eight-hour cap cuts short (REPORT-143 R17).
- **R26.** **The ceiling.** A manifest declaring more than `PACKAGE_MAX_DURATION_SECONDS` is refused, written `failed` with the declared value and the ceiling. A manifest without a positive integer `expected_duration_seconds` is refused too. The default is 7,200, and a test asserts it equals the contract fixture's `limits.max_duration_seconds` (REPORT-167 R26). A configured value that is not an integer, is below that default or is above 28,800 stops the runner at startup with the reason, before it serves a hook, since a lower ceiling would refuse packages report-server accepts and a higher one would let a claim fail REPORT-143's rules. The value written onto a claimed result is the declared one, which is then at most the ceiling and at most 28,800. report-server refuses more than 7,200 at publish (REPORT-167 R21), so this check binds only on versions published before that.
- **R27.** **The in-VM timeout** bounds each package's process at its declared duration plus 10 minutes, the margin the watchdog uses, unless `PACKAGE_TIMEOUT_MS` overrides it. It is kept for a runaway on a VM that stays awake: a hung package keeps heartbeating (R44a), so REPORT-143's lease never ends it, and this timeout does. When it fires, the package uid's processes are killed (R28a's kill) and its step given up to 10 seconds to end before the failure is written, a cancelled run writes no later stage, and the sandbox's own bound kills with SIGKILL, so nothing of a timed-out package runs on into the next package's turn as the same uid. The lease, not this timeout, is the stall guard for a runner that stops (`final-design.md` 7.2).

### Running a package

- **R28.** **Every per-package path is keyed by the identity**, through its package key (the identity with `/` as `__`, a single path segment): the package's home `<workRoot>/home/<package_key>`, its input directory `<workRoot>/in/<package_key>`, its output directory `<workRoot>/out/<package_key>`, and the fetch cache `<workRoot>/packages/<package_key>/<version>.zip` with the archive unpacked beside it. The output directory is emptied before each run, so a package that writes no `display.md` cannot be credited with its last run's.
- **R28a.** `/work` and the directories under it that hold the per-package paths belong to the runner (root), and only the package's own home and output directory are handed to the package's uid, so a package cannot replace a directory the runner later reads as root. The runner reads `display.md`, `summary.txt` and `counts.json` without following a link: the output directory must resolve to itself, and each file must be a regular file opened with `O_NOFOLLOW` and `O_NONBLOCK`, so a named pipe left in a file's place is refused rather than blocking the runner's process. A link is refused, so a package cannot have root copy a file it could not read itself into its result. Likewise, the ownership walk that hands the class data directory and the cc-data root to the package's uid follows no link: a link there is skipped and every change of owner is an `lchown`, so a link left by one run cannot make the package the owner of the link's target at the next. A file with more than one hard link is neither handed over, read, nor synced to S3, and the syncer, running as root over the package's tree, opens each file it uploads with `O_NOFOLLOW` and `O_NONBLOCK` and skips anything that is not a single-linked regular file at the path it scanned, so nothing swapped in after the scan is read or blocks a flush: `fs.protected_hardlinks` is not relied on, since whether the VM's root may set it is not recorded, and the two checks close both paths without it. Before reading, after every run whether it succeeded, failed or timed out, the runner kills every process the package uid owns (`kill -KILL -1` run as that uid) and repeats until `pgrep -u <uid> --runstates R,S,D,T,t` finds none (a killed orphan stays a zombie, unreaped while the runner's node is PID 1, and a zombie runs nothing), failing the package if five kills do not clear them or the check cannot run. Every package runs as the same uid, so a process one left in the background could otherwise write the next one's output, or swap its output directory between the check and the read.
- **R29.** The result document id is the package key, derived by the runner from the identity. `/work`'s own `package_key` is not used, and the runner refuses a package whose `package_key` disagrees. The one exception is an identity that fails the grammar (R6): its refusal is written at `/work`'s `package_key` when that is itself a well-formed key, since nothing else addresses the result, and an entry with neither is logged and left.
- **R30.** The archive is fetched from `packages/<identity>/<version>.zip` (`PACKAGES_PREFIX` and a `packageKey(identity, version)` beside it, RD-4 pass 1 Q4), in both backends, and verified against the checksum `/work` handed out, which rigse took from the catalog. It is fetched and verified once per VM for an identity, version and checksum; later plans reuse the verified manifest and the unpacked copy, which sits under the root-owned work root (R28a).
- **R31.** The archive is unpacked only after the checksum passes, and its **actual** inflated size is bounded: the runner counts the bytes `unzip -p` produces and refuses the archive past 50 MiB (REPORT-142 R6's limit) before extracting anything. After extraction, an archive holding a symbolic link is refused and its directory removed, and every unpacked entry's mode is set to 0755 for a directory or an executable file and 0644 otherwise, since unzip restores the archive's modes and every package runs as one uid that could otherwise rewrite another package's cached code. No entry can land outside the package directory: Info-ZIP writes a `../` or absolute entry inside the destination (Stage 1 verification), so the runner does not check for one.
- **R32.** The manifest is read from the verified archive. Its `name` must equal the identity's last segment and its `version` the version handed out, or the package is refused. `entrypoint` must stay inside the package directory, as today.
- **R33.** A refused or failed fetch writes the result `failed` with the reason, never `running`, and goes on with the next package.

### Applicability

- **R34.** **The runner decides, report-server matches.** A manifest whose `urls` declares no pattern in any group applies to every class, and no call is made. Otherwise, before claiming, the runner reads the class's profile document `classes/{class_hash}` through that class's store and asks `POST <report_server_url>/api/v1/packages/applies` with its own report-server token as the bearer and the body `{urls: <the manifest's urls, as read from the verified archive>, scope_urls: <the profile's assignment_urls and interactive_urls together>}`, sending no `assignment_urls`, so nothing is derived and the answer matches the profile the app's list matched (REPORT-167 R15, R19). A yes is kept for that class, identity and version until the next resume, so a re-plan after each package (R7) does not ask again. `applies: false` writes the result `failed` with "the package does not apply to this class: <reason>", report-server's reason verbatim. A package that declares patterns on a class with no profile document is refused with "this class's authored profile has not been derived yet", without a call.
- **R35.** **What the runner makes of the other answers.** A profile that cannot be read, a 503, a 5xx, an answer without a boolean `applies`, a network failure, and no answer within 30 seconds each count as a failed claim attempt (R9), logged as `report_server.refused` with the status. The third one writes the result `failed` with "report-server could not say whether the package applies to this class (<reason>); run it again", so a report-server outage drains the queue and the VM can suspend, where a package left queued would hold it awake until its cap (R9, since `/idle` declines to suspend with work queued). A 400 or 422 is a refusal: the result is written `failed` with report-server's message, since it says the request is one report-server will never accept: publish already checks patterns with the applies route's rules, and the profile's URLs are within the route's bound, so a 400 means the runner and report-server disagree on the contract, which no retry fixes (Q18). A 401 or 403 means the runner's report-server token is no longer good, which nothing in the VM can fix: it is a failed claim attempt too, logged with the status. The runner never reads a 404 as "the route is not deployed"; it is a failed claim attempt like any other unexpected answer.
- **R36.** The runner holds no matcher and no copy of `fixtures/url-patterns.json`, which is report-server's test file (REPORT-167 R8). A test pins R34's request (the path, the bearer, the body's two keys and that `urls` is the manifest's as read from the archive) and R35's handling of each answer against a stub report-server.

### What the package is handed

- **R37.** **`scope.json`** is written into the package's input directory, readable and not writable by the package's uid, and named in `RD_SCOPE_FILE`. It holds `kind`, `id`, `classes` (a list), `assignments` with `{offering_id, runnable_id, name, url}`, all four from the `/work` scope block, `clue_source`, `dataset` and `output_dir`. `clue_source` is `"cc-data"`: packages read CLUE only through cc-data, and the key stays until REPORT-152 removes it from cc-data-cli's scope file, its docs and package tests, which all expect it today. Until then cc-data-cli's `package run` (`internal/packages/run.go` on `main`) and REPORT-147's test still write `"firebase"`; no package reads the value, so the two differ harmlessly. The smoke `image` command writes `"cc-data"`, as the runner does (R52).
- **R38.** `RD_CLASS_HASH` and `RD_PORTAL_CLASS_ID` are deleted from the package's environment. The rest stays: `HOME`, `PATH`, the proxy variables, `CC_DATA_ROOT`, `CC_DATA_LOCAL`, `CC_DATA_PORTAL`, `RD_DATASET`, `RD_DATA_DIR`, `RD_OUTPUT_DIR`, `RD_REPORT_SERVER_URL`, `RD_BUCKET` and `RD_STORAGE_PREFIX`, with `RD_SCOPE_FILE` added.
- **R39.** **The dataset** is `pkg-<catalog id>`, from the catalog id `/work` handed out. `RD_DATASET` is the full ref `<portal host>/pkg-<catalog id>`, and `scope.json`'s `dataset` is the bare name `pkg-<catalog id>`, which is what `cc-data package run` writes and REPORT-147's tests encode (Q13). It is keyed to the package, so a new version reuses the last version's pulls (`final-design.md` 5.3).

### What the package writes

- **R40.** The runner reads `display.md` (required) and `summary.txt` (optional; its first line, trimmed, becomes `summary`) from the output directory. `display.json` is no longer read.
- **R41.** **The display cap** is 64 KiB of UTF-8 bytes, cited from `final-design.md` 10 as the one place the number lives. A larger `display.md` is refused: the result is written `failed` with its size and the limit, and nothing of it is stored. It is never truncated.
- **R41a.** `counts.json` stays the channel for what the package counted: `answers`, `logs` and `log_freshness_at` are read from it, and nothing else. Each is optional: `wildfire-responses` writes only `answers` (REPORT-147). `final-design.md` 10 names it, by this pass's earlier sharpening (Q10).

### The documents

- **R42.** **One result per researcher per package per class**, at `researcher_dashboard/{portal}/classes/{class_hash}/researchers/{platform_user_id}/results/{package_key}`, written through that class's store. The shared `classes/{class_hash}/results/` is not written, and `requested_by` is gone.
- **R43.** A result claimed is written `status: "running"`, `stage: "starting"`, `package: {identity, version, checksum}`, `image_version`, `microvm_id`, `expected_duration_seconds`, `heartbeat_seconds: 60`, `started_at`, `finished_at: null`, `error: null`, `summary: null`, `display: null`. REPORT-143's rules refuse a `running` write without `heartbeat_seconds` (an integer 30 to 120), so a claim without it fails on every stack. A result refused before its claim is written `status: "failed"`, `error`, `finished_at`, with `package`. Stages are written as they begin: `prepare_package`, `run_package`.
- **R44.** A result finished is written in one call: `status: "done"`, `stage: "done"`, `package`, `image_version`, `summary`, `display`, `finished_at`, `error: null`. A run that fails is written `failed` with the redacted reason, `stage` left at the stage it failed in. **The runner's fields on a result describe only its latest run**: the claim clears the last run's `summary` and `display` (Q8). `previous`, the last finished run that `/run-package` writes when it re-queues a package (REPORT-143 R8a), is not the runner's: every runner write to a result (the claim, a stage, a beat, the finish and a failure) merges named fields and never names `previous`, so it survives them all, and a test pins that it survives a claim, a finish and a failure.
- **R44a.** **The heartbeat** (REPORT-143 R17, Q13). From the claim until the run's final write, the runner merges `{platform_id, updated_at}` (server time) into the result every 60 seconds through the run's own class store. The interval and the claim's `heartbeat_seconds` are one constant, so they cannot disagree, and it is not configurable, since the rules bound it at 30 to 120. A beat is skipped while the previous one is unsettled, so a slow Firestore never stacks writes. Before the final write (`done`, or `failed`) the timer is stopped and any beat in flight is awaited, so no beat lands on a finished result and bumps its `updated_at`. A beat that fails is logged as `heartbeat.failed` and does not fail the run: the lease fails it only if beats stop for five minutes. The beat runs while the package does, including across a suspend and resume; REPORT-143's wake writes `resumed_at`, which restarts the lease.
- **R44b.** **A run's final write settles before anything else is written.** The run's final write, `done` or `failed` (a `failed` after a `done` the SDK rejected included), is awaited until the SDK's write promise resolves or rejects, never cut short by a local timeout, since a write the runner stopped waiting for can still land. Until it has settled, the run's class store stays open and the runner writes nothing else: no runner document write (R8), no other result and no next claim. A final write that never settles leaves the runner waiting with its heartbeat stopped, which the lease answers: the watchdog terminates the VM and fails the result. `/terminate`'s failure write is the exception, bounded like every hook write (R21, R23), since the hook has 60 seconds and the VM ends after it; the runner-document write that follows it names the run in `current_package` (R8), so REPORT-143's moved-on case cannot read it as the runner having moved on.
- **R45.** Every runner write to a result or to `runners/` carries `platform_id` and sets `updated_at` to server time, and every other timestamp the runner writes to Firestore (`started_at`, `finished_at`, `last_pull_at`) is server time too, since no clock inside the VM is real after a suspend. The one exception is the status document's `expires_at`, computed at `/run` from a VM that has just booted.
- **R46.** **The counts** are written after each successful run onto `classes/{class_hash}/researchers/{platform_user_id}`: `platform_id` and `data: {answers, logs, last_pull_at, log_freshness_at}`, with `last_pull_at` server time, and `log_freshness_at` the package's value as a Firestore timestamp when it parses as a date, and absent otherwise. The write replaces `data` as a whole: a count the package did not write is absent, never left over from an earlier run of another package, since a merge keeps the old value beside the new ones (Q17). So any of `answers`, `logs` and `log_freshness_at` can be absent, which RD-3 renders as not reported, and `last_pull_at` is always present. Nothing is written to `classes/{class_hash}`.
- **R46a.** The status document's `scopes` replaces `classes`: the class hashes the synced tree holds data for, plus the one being run.

## Technical Notes

- **What can only be learned on a real VM**, each named so a staging run can answer it:
  - whether `/run`'s body carries `microvmId` (REPORT-143, Technical Notes; R1 makes a missing one fail `/run` at once);
  - whether an API `SuspendMicrovm` delivers `/suspend` (REPORT-143 R1; R22's log line and the pre-`/idle` flush). REPORT-143 plans to answer it after its own deploy, on a VM from `main`'s image suspended by an operator, so it may be answered before this pass ships; R22 does not depend on the answer either way;
  - whether the Firebase refresh token still yields an ID token after a suspend longer than an hour, which the post-resume `/work` depends on (`final-design.md` 7.1 records that the SDK's own timer-driven refresh did not survive, and not why);
  - whether the VM's wall clock advances across a suspend (R15 does not depend on it; R25 does, and the watchdog backs it);
  - how Lambda hands the execution role to the VM (the spike found IMDS, `sandbox.js`); R16 disables both that and the environment;
  - whether anything in the image or the base image makes an AWS call of its own (the image's only AWS dependency is `@aws-sdk/client-s3`, `runner/package.json`).
- **A profile URL is always within report-server's bound.** The function bounds a profile URL at 2,048 UTF-16 code units (`derive-profile.ts` line 207, `derive-profile-route.ts` line 42), and REPORT-167 bounds a scope URL at 2,048 code points, which a URL never has more of; REPORT-167 aligned it after this spec found a byte bound would refuse a non-ASCII URL near the limit (channel #28, #42).
- **The watchdog's `terminated` write and the runner.** The watchdog writes `runners/{uid}` `terminated` only for a VM that is gone, and only while the document names that VM and is not already terminal (REPORT-143 R17, R19a), so the runner that wrote the document last never runs again to see it, and a newer VM's document is never touched. R8's write-once `ready` is unaffected.
- **The fixture's `limits` and the runner's.** `limits.max_duration_seconds` is R26's default. `limits.max_url_length` is report-server's and the function's; the runner sends the profile's URLs as stored and lets report-server judge them (R35), so it keeps no copy of that number.
- **The watchdog's view of a running package.** The heartbeat (R44a) is the only proof of life REPORT-143's lease reads. A runner that stops beating, through a crash, a hung event loop or a final write that never settles, has its VM terminated and its result failed within about 7 to 9 minutes. A package that hangs while the runner beats is bounded only by R27's timeout.
- **Why the moved-on case cannot fail a live run.** REPORT-143 fails a stale result without a kill when the runner document names the same VM, is not terminal, names another `current_package` and was written after the result. Only two runner writes change `current_package`: the next claim's and the drained `ready` (R8), and both wait for the last run's final write to settle (R44b). The hooks write the outstanding run's own `current_package`, and leave the field alone when none is outstanding. So a document naming another package means the earlier run's last write has already resolved or been refused, and nothing will write that result again.
- **Ordering within one store.** The beat, the final write and `/terminate`'s failure all go through the run's class store, and the Firestore SDK sends one instance's writes in the order they were made. So `/terminate` stops the beat's timer and writes the failure without waiting for a beat in flight, which would spend the hook's 60 seconds on a write that lands first anyway.
- **`microvm_id`'s form is checked by `/work`.** REPORT-143 compares the runner's `microvm_id` with `vms/`'s, which holds `RunMicrovm`'s id, in R17's same-VM tests and R19a's guard. The runner writes `/run`'s `microvmId` unchanged (R1, R8, R43), and `/work` answers 409 to any id that differs from `vms/`'s by exact string comparison (REPORT-143 R6a, `vm-routes.ts`), so a runner that has claimed anything has already shown that the two forms agree. A differing form would show as a VM that never takes work, a 409 on every `/work` after its first minute. The first staging run compares the logged id with `vms/` all the same (morning review item 2b).
- **The runner's VM is not relaunched when its window runs out.** REPORT-141's function reuses a `RUNNING` VM whatever its age, so a package failed with "VM window exhausted" and run again lands on the same VM until it reaches its cap. That is the function's behavior and is recorded for REPORT-143's follow-up, not changed here.
- **`STATUS_BACKEND` is `FIRESTORE` or `MEMORY`.** Every call to the function needs the session's ID token, so a store that signs nothing in could never pass `/run`'s claims check (R3); `LOG` is refused at startup. RD-1's spec (`0cf3f1c`) drops the `StatusBackend` parameter and fixes `STATUS_BACKEND=FIRESTORE` on the image.
- **`RD_DATA_DIR` is shared by every package of a class.** The per-package paths of R28 are the runner's; the class's data directory stays shared, since it holds the researcher's pulled corpus. A package that keeps state there under a file name it chooses (the spike's `_lib` wrote `runs.json`) can collide with another package's, so REPORT-147's packages keep their state in their own dataset (`pkg-<catalog id>`, R39).
- **`/run` stays inside 60 seconds** with one more upstream call (the credentials, bounded at 15 seconds). The spike measured `/run` at 4.5 seconds with a two-second pull-down (`design.md`, criterion measurements); a large prefix's pull-down is the risk it already was.
- **A runner token cannot write the scope document's timestamp as server time only by rule.** REPORT-143's rules require server time on `runners/` and results, not on `classes/{h}/researchers/{uid}`; R45 applies it there too, by choice.

### RESOLVED: Q1. Does the runner poll `/work` while idle, and for how long does it stay awake?
**Context**: R10. `/run-package` does nothing to a VM that is already running (REPORT-141, "ensures a VM exists"), so work requested on a warm idle VM waits for its next `/work` or `/idle`. The watchdog suspends an awake VM with nothing queued after 30 minutes without activity, counting the runner document's `updated_at` (REPORT-143 R18).
**Options considered**:
- A) No polling: one `/work` when the queue drains, then `/idle` after the idle period. Work requested during the period waits up to the whole period.
- B) Poll `/work` every 30 seconds through a 5-minute idle period, then `/idle`.
- C) Listen to the runner's own status document, whose `queue` the function writes on append, and call `/work` when it becomes non-empty.

**Decision**: B (stage 2, from the code). The warm-before-class case is the one the pull model exists for (`final-design.md` 6.1), and under A the researcher who clicks a second package a minute after the first finished waits minutes for a VM that is awake. C is quicker, but it is a long-lived Firestore listener on a store that R4 makes per request, and its token goes stale on the SDK's own timer, which is what failed in `final-design.md` 7.1. Polling costs at most ten `/work` calls per idle period, each one session-token mint and one Firestore transaction (REPORT-143 R9). Five minutes is the spike's platform idle timer (`spike-plan.md` 10), which the warm case was measured against, and it leaves the watchdog's 30 minutes six times over. Both numbers are code defaults with environment overrides (`IDLE_PERIOD_MS`, `IDLE_POLL_MS`), so changing them is a runner release, not a stack change.

#### RESOLVED: Deleting the previous request's stores could pull one out from under a running package
R4 deleted the last request's stores when a new session was signed in. R20's post-resume cycle adopts a new session while a package suspended mid-run may still be running, and that package writes its finish through its own class store. A write through a deleted app fails (`failed-precondition`, stage 3 verification). Fixed in R4: a class store in use is kept until its package finishes. R20 now claims nothing until that package is done.

#### RESOLVED: The window measured from `/run` ran past the VM's cap
Lambda counts `maximumDurationInSeconds` from the launch, a few seconds before `/run`, and at the cap the `/terminate` hook still needs time to flush. A package fitting the window exactly would be cut off. #### RESOLVED: REPORT-143 contract owner: a failed claim-time runner-document write lets the watchdog fail a run suspended mid-run
R8 keeps `current_package` during a run "by not writing the field", which assumes the claim's own runner-document write landed. That write is a bounded hook-style write (`writeFromHook("work", …)` in `#runPackage`) whose failure is only logged. If it fails, the document still names the previous package or `null`, and the next hook write (`/suspend`'s `suspending` and `suspended`) bumps its `updated_at` past the result's last beat. REPORT-143's watchdog checks moved-on before the VM's state (`watchdog.ts`, the `leaseLapsed && movedOn(...)` branch), so five minutes into the suspend it fails the result with no kill; on resume the run finishes and its `done` replaces the `failed`, so the row flips. Verified: throwaway test REVIEW B (claim lands, the claim's runner-document write throws, `/suspend`) leaves the result `running` and the document `suspended` with `current_package: null`, and `watchdog.ts`'s `movedOn` predicate, transcribed, answers true; with `current_package` naming the run (REVIEW B2) it answers false. Odds are low (a failed Firestore write at the claim, then a suspend mid-run).

- A) While a run is outstanding, every runner-document write (the hooks' included) writes `current_package` from `#run` explicitly, so a lost claim-time write is repaired by the next one. R8 and R22 change from "by not writing the field" to "by writing the run's own value"; the `/suspend` test asserts the value rather than its absence.
- B) The claim-time runner-document write is retried until it lands, and the package does not start until it has (or the run is failed after three tries, as R9).
- C) Accept it: low odds, and the row recovers when the run finishes.

**Recommendation**: A. It is a few lines in `#runPackage` and the hooks, it covers every later write rather than one retry, and R8's invariant then holds whatever any single write did.
**Decision**: A (Doug, 2026-10-14). R8, R22, R23 and R44b now say the hooks write the run's own `current_package`; implementation step 5 builds it, with REVIEW B as its test.
