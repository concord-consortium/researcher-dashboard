# RD-4 pass 2: the pull loop, and everything else in the runner, on the broker's credentials

**Jira**: https://concord-consortium.atlassian.net/browse/RD-4

**Status**: **Closed**

**Pass**: 2 of 2, the last; pass 1, the `scripts/` to `packages/` prefix rename, is `specs/RD-4-pass-1-packages-prefix.md`. Branch `RD-4-pass-2-pull-loop`, on `main` with RD-1 and pass 1 merged. Released to the QA stack from the branch before review (R58).

## Overview

Turn the spike's runner into the pull-model runner of `final-design.md`: it stops being dispatched to, asks report-service for its work (`POST /work`), its storage credentials (`POST /storage-credentials`) and its suspend (`POST /idle`), and makes no AWS call on the Lambda execution role. Every per-package path, the archive key, the result document and the cc-data dataset are keyed by the package's identity and catalog id; applicability is asked of report-server and enforced by the runner; the package is handed `scope.json` and writes `display.md` and `summary.txt`; the result becomes one document per researcher per package per class, with the counts on the researcher's own scope document; the lifecycle hooks follow `final-design.md` 7.1 and 7.2; `POST /refresh-token` and the dispatch route are deleted; section 3's renames land; the CLUE pre-pull is deleted; the image's cc-data moves to the pre-release carrying the package commands; and a smoke script gates the image.

## Project Owner Overview

Before this pass the researcher's machine waited to be told what to run, and it read and wrote student data with one shared AWS permission that reached every researcher's data. After it the machine wakes, asks for its own work, runs it, and asks to be put back to sleep, and every byte it stores or fetches goes through short-lived credentials that reach only its own researcher's folder and the published packages. RD-1's runner stack is built without the shared permission, so this runner is the first that can work on it at all.

Researchers see the difference as behavior that used to break: a machine that slept for two hours wakes and runs the work waiting for it, each researcher's results and counts are their own, a package that does not suit a class is refused even if something offered it, and two packages with the same name from different authors no longer collide. It is also the runner the first real package (Wildfire's open responses, REPORT-147) runs on.

## What it builds on

- **REPORT-167** (report-server): `POST /api/v1/packages/applies`, the only glob matcher, and `fixtures/package-contract.json`, the identity, version and package-key cases and `limits`.
- **REPORT-146** (cc-data-cli `v0.3.0-pre.1`): `cc-data package init | run | build | publish` and the `run_answers` view; `cc-data package run` reproduces this runner's package environment on a laptop.

## Requirements

### The pull loop

- **R1.** `runHookPayload` must carry `function_url` beside the fields it carries today, and the runner reads its own MicroVM id from `/run`'s body as `microvmId`. `/run` fails (500, so Lambda destroys the VM) when either is missing, because `/work` and `/idle` refuse any call without the VM's own id, and a result cannot be written `running` without `microvm_id` (REPORT-143 R6a, R10, R22a). A VM that cannot take work is stopped at once rather than left awake until the watchdog or the eight-hour cap.
- **R2.** The runner calls `POST /work` with `{microvm_id}` as `/run` returns (started by it, never awaited by it, since `/run` has 60 seconds), after every resume, after every package finishes, and while idle (R10). The call authenticates with an ID token of the current session store, forced fresh after a resume (R20), and every call to the function is bounded at 15 seconds. A 409 in the first 60 seconds after `/run` is retried every 5 seconds; after that, and for any other failure, the runner waits one idle poll interval (R10) and tries again, logging each failure. A failed `/work`, a refused adoption (R3) and a failed credential fetch after a resume (R15) each count toward the idle period as a poll that found nothing does, so a failure that keeps repeating still flushes and asks `/idle` once the period has passed, rather than keeping the VM awake until its cap. `/work` is never called from inside a lifecycle hook.
- **R3.** Every `session_token` the runner is handed, at `/run` and in each `/work` answer, is used to sign in a new session store, and the runner reads that store's verified ID-token claims: `platform_user_id` must equal the payload's, `platform_id` the payload's, and `researcher_dashboard_runner` must be `true`. A token that fails the check is not adopted: at `/run` the hook fails; from `/work`, that answer is discarded, nothing it names is run, and the failure is logged. `firebase_project` in a `/work` answer must equal the payload's.
- **R4.** Stores are per request, never per VM. Each `/work` answer that is adopted gets its own session store and, for each class it names, its own class store, signed in with that answer's class token for `firebase_project` before the first write for that class. A store is never reused by a later request; the previous request's stores are deleted (`deleteApp`) once the new session is signed in, except a class store a running package is still writing through, which goes once that package's final write has settled (R44b).
- **R5.** A class token is used only if its store's verified claims name the payload's `platform_user_id` and `platform_id`, carry the runner claim, and carry the `class_hash` of the class it is keyed under. A class whose token fails, or whose `firebase_project` token is missing, has its handed-out packages skipped for that request, logged, and not claimed (its results cannot be written, R42).
- **R6.** For each adopted `/work` answer, the runner reads each class's scope block, validates it (`kind: "class"`, `id` equal to the class hash, `classes` a one-element list naming that hash and a positive integer `class_id`, `assignments` a list), and takes the packages in the order given. Any package whose identity, version, checksum or catalog id does not match the catalog grammar (identity `^(users|projects)/[1-9][0-9]{0,17}/[a-z0-9][a-z0-9-]{0,62}$`, version `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(-[0-9A-Za-z.-]+)?$` and at most 64 characters, checksum `^sha256:[0-9a-f]{64}$`, catalog id a positive integer) is failed with the reason (R43), not run. A test asserts the identity and version checks and the package key (R29) against every case of REPORT-167's `fixtures/package-contract.json`, which this repository holds as a byte-identical copy at its own `fixtures/package-contract.json`, kept in step by `runner/scripts/contract.mjs` (Q14): `npm run contract:sync` fetches report-service's file from GitHub (`master` by default, or `--ref`) and writes the copy, and `npm run contract:check` fails when the copy differs. The release (R58) and the monthly rebuild (R54) run `contract:check`, and so does CI on every push touching `runner/` or `fixtures/`.
- **R7.** **Claiming.** A package is claimed by writing its result `running` (R43). Before the claim, the runner has fetched and verified the archive (R30), read the manifest, applied the ceiling (R26) and the window (R25), and checked applicability (R34); a package refused at any of those is written `failed` directly, never `running`. One package runs at a time. After a package finishes, the runner calls `/work` again rather than continuing through the previous answer, so work appended meanwhile is seen, and each package's writes use tokens minted seconds before it started.
- **R8.** **The status document** `runners/{platform_user_id}` is written through the session store. On a claim: `state: "running"`, `current_package: {class_hash, package_key}`, and `queue` set to the answer's remaining queued entries as `{class_hash, package_key}` pairs, excluding the claimed one and any the same plan wrote `failed`. After a resume while a run is held, the post-resume cycle writes `state: "running"` with that run's `current_package` (R20). When `/work` hands out nothing runnable: `state: "ready"`, `current_package: null`, and `queue` set to the entries still queued, with a well-formed key, that the runner can neither run nor write (R9), usually `[]`, written once when the queue drains and not again on each idle poll while that list is unchanged; a package refused while the VM is drained is a change, so `ready` is written again to take it off the `queue` the function wrote on append. The loop's writes (the drained `ready`, the claim's `running` and the post-resume `running`) commit only while no `/suspend` has begun, tested in the write's own transaction, so one sent before the hook cannot land over `suspending` or `suspended`; a claim's write skipped that way is repaired by the hook's writes, which name the run, and by the post-resume `running`. Every write carries `platform_id` and `updated_at` as server time (REPORT-143 R22a). The function also writes `queue` on append, so it may lag by one write (REPORT-143, "For RD-3"). **While a run is outstanding, every write to this document writes `current_package` naming that run**, the `/suspend` and `/terminate` hooks' included, taken from the run the runner holds, so a claim-time write that was lost is repaired by the next one rather than leaving the previous package or `null` behind; a hook with no run outstanding leaves the field alone. Only the next claim or the drained `ready` names something else, and both come after the run's final write has settled (R44b). That is what makes REPORT-143 R17's moved-on case safe: a document naming another package means this run will never be written again. The runner writes `microvm_id` exactly as `/run`'s body gives it, on this document and on every claim (R1, R43).
- **R9.** A claim write that is refused or fails leaves the package unclaimed. The runner logs `package.claim_failed` each time, tries again after one idle poll, and after the third failed attempt in an awake period writes the entry refused (`failed`, "the runner could not record its claim on this package ...; run it again"), since `/idle` answers `work_queued` while it stays queued. If that write fails too, the runner stops trying the entry for the awake period and goes on with the rest, so the idle loop (R10) runs, and the VM stays awake polling at 30 seconds until the entry is resolved or the VM reaches its cap. So does an entry whose class has no store (its class token missing or refused): it is logged as `package.skipped` and the drained `ready` lists it in `queue` (R8), which is what REPORT-188 reads to fail it. An entry with neither a usable identity nor a well-formed `package_key` has no result to write and nothing to list, so it is only logged; report-service's `/work` derives `package_key` from an identity checked when the package was queued, so it does not arise, and if it did, nothing would resolve it before the VM's cap. A fetch that fails for the broker, S3 or the network (`PackageFetchFailed`) counts as an attempt the same way, and the third is written refused with "run it again"; an archive refused for what it holds (missing or unreadable, a checksum mismatch, over 50 MiB unpacked, a link, a manifest that does not match) is written refused at once. The count is for one awake period and one queued run: it is cleared once the entry is claimed or written refused, and on every resume, so a package run again starts with three attempts (REPORT-143 re-appends a finished package).
- **R10.** **Idle.** When `/work` hands out nothing, or a call fails (R2), the runner polls `/work` every 30 seconds (`IDLE_POLL_MS`) until 5 minutes (`IDLE_PERIOD_MS`) have passed since it last had work, then flushes and verifies the sync (R22's fallback, always on) and calls `POST /idle` with `{microvm_id}`. Both are code defaults with an environment override, not stack parameters. Five minutes is well under the watchdog's 30-minute idle sweep (REPORT-143 R18), and polling keeps a run requested on a warm idle VM from waiting for the idle period, since `/run-package` does nothing to a running VM (REPORT-141).
- **R11.** `/idle` answering `work_queued: true` sends the runner straight to `/work`. `suspended: true` ends the idle loop: the `/suspend` hook follows. An answer with neither (`run_in_progress: true`, or anything else) is logged as `idle.declined` with the answer, and the idle period starts again, as after a failed call, so the runner does not call `/work` and `/idle` back to back with no sleep for as long as the function declines (landing tracker 3.2a). A 409 or 502 is logged and the runner returns to polling. A flush that does not verify skips the `/idle` call for that period, since a suspend without a proven flush is what `/suspend` exists to prevent.
- **R12.** **The `/idle` race.** Each resume starts a new epoch in memory. An answer or error from a call started in an earlier epoch is ignored, so a slow `/idle` answer that arrives after the VM has been suspended and resumed is not read as a failure or as permission to do anything (REPORT-143 R10, R11). A loop from an earlier epoch makes no further call either, so a pre-`/idle` flush that ends after a resume does not call `/idle`, which would suspend the VM under the new loop's running package.
- **R13.** The runner never lets the queue or a token reach a browser: it writes package keys and class hashes to documents the researcher already reads, and nothing else from `/work`.

### Storage credentials and the default chain

- **R14.** Every S3 client the runner builds is built from `/storage-credentials` credentials, with explicit `accessKeyId`, `secretAccessKey`, `sessionToken` and `region`, in one module, which refuses to build a client without all four. That covers the syncer's pushes, deletes and flushes, `/run`'s pull-down, and the package fetch. Nothing else in the runner imports an AWS SDK client.
- **R15.** The credentials are fetched with the current session store's ID token and checked against the wall clock immediately before each use: a credential within 5 minutes of its `expiration` is fetched again. Nothing refreshes them on a timer. A resume marks them stale (R20), so the first S3 call after a resume always fetches new ones whatever the VM's clock says. The response's `bucket` must equal the payload's and its `prefix` must be `researchers/<platform_user_id>/`, or the runner refuses to use it.
- **R16.** **The default chain is switched off in the runner's process** before anything else runs: `AWS_EC2_METADATA_DISABLED=true`, and every environment variable the SDK's default provider reads for credentials (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_PROFILE`, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, `AWS_CONTAINER_CREDENTIALS_FULL_URI`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_ROLE_ARN`) removed, with the shared credentials and config files pointed at `/dev/null`. So a default-chain client left anywhere fails with `CredentialsProviderError` at once, which names its cause, rather than with an `AccessDenied` from the execution role, which on RD-1's stack holds no S3. The switch is made when the process starts, which on a MicroVM is the image build before the snapshot, so each VM's `/run` reads its own environment and logs `aws.default_chain_disabled`, or `aws.default_chain_enabled` with the variables still set.
- **R17.** Tests: a source test that `new S3Client` appears in exactly one module and nowhere else in `server/`, and that no other `@aws-sdk/*` client is imported; a unit test that the builder refuses missing credentials; a test that a client it builds resolves exactly the broker's credentials while `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` hold sentinel values in the environment; a test that with R16 applied, `new S3Client({})` rejects `credentials()` with `CredentialsProviderError`; a test that `S3Backend` has no default client; and a test that `/run` in S3 mode fetches credentials, with the session's ID token, before its first S3 call.
- **R18.** A package archive that cannot be read is reported as "`packages/<identity>/<version>.zip` is missing or not readable", whether S3 answered `AccessDenied` or `NoSuchKey`, since without a list grant a missing key reads as `AccessDenied` (RD-1 pass 2, Technical Notes). Any other failure of the fetch, the storage broker's or the network's, is reported as "could not be fetched" with its own message, and logged with the error's name and message, since it is not the package's absence.
- **R19.** The syncer's interval does not start at `/run` until the credentials have been fetched and the pull-down has finished, and after a resume not until the post-resume `/work` has been adopted and credentials fetched (R20); `/suspend` stops it. While the VM is awake a tick uses the credentials like any other call, so one that finds them within R15's margin of their expiry fetches new ones.

### The lifecycle hooks

- **R20.** **`/resume` writes nothing.** It marks the session, class stores and storage credentials stale in memory, starts a new epoch (R12), arms the held run's bound again with what was left of it (R27), and returns 200 at once. The post-resume cycle then runs outside the hook: an ID token forced fresh from the last session (bounded by a timeout), `/work`, adoption (R3, R4), credentials (R15), the syncer (R19), then the queue, once any package that was running when the VM was suspended has finished. The status document keeps whatever `/suspend` wrote until that cycle writes (`final-design.md` 7.1(a), 7.3). With a run held across the suspend, the cycle writes it `running`, naming that run (R8), as soon as it has adopted the fresh session, so the page does not show a working VM as suspended for the rest of the run; it does not once that run's final write is under way, which settles before anything else is written (R44b). The write changes nothing REPORT-143 reads: its rules do not constrain `state`, its lease and suspended bound come from Lambda's state and the result's timestamps, and its moved-on case needs another `current_package` (Q21).
- **R21.** **Every other hook's status write is bounded** at 10 seconds, catches its failure, logs `status.write_failed`, and records it in memory; the next successful status write carries the last ten recorded failures as `status_write_failures: [{hook, error}]`, each error redacted as result errors are (`log.js` `redact`), and clears them. Every runner-document write carries the field, empty when nothing is pending, so a reported failure leaves the document with the next write, and a failure recorded while a write is in flight waits for the one after. No hook returns non-200 because a status write failed. The failures that still fail a hook are the ones that should: `/run`'s payload, `microvmId`, token claims, sandbox verification, credential fetch and pull-down (R1, R3, R16); `/suspend`'s and `/terminate`'s flush verification (R22, R23).
- **R22.** **`/suspend`** pauses an outstanding run's bound (R27), writes `suspending` (bounded), stops the package's processes if a run is outstanding (`kill -STOP -1` run as the package uid, repeated until `pgrep -u <uid> --runstates R,S,D` finds none, at most five times, and bounded at 10 seconds; a failure or the bound is logged as `package.freeze_failed` and the flush goes ahead), stops the syncer's interval, flushes and verifies, and writes `suspended` (bounded) only when the flush is proven. A package still writing would otherwise fail the verify, so only a real storage failure refuses a suspend. The stop is retried at most five times, 200 ms apart, since a process inside a write stops only once the write returns. `/resume` continues the stopped processes (`kill -CONT -1` as the package uid) without awaiting it, once a stop that outlasted the hook's 10 seconds has ended, a failure logged as `package.thaw_failed`. A claim that lands while `/suspend` runs starts its package only after the resume, since a package started during the flush could fail the verify; if the suspend is refused, it starts nothing. Both writes keep `queue` by not writing it, and `current_package` as R8 says: the outstanding run's, written again, or left alone while idle. A flush that does not verify returns 500, which is the deliberate exception (`final-design.md` 7.1(a)). Lambda terminates a VM whose `/suspend` answers 500 and delivers no `/terminate` (`design.md` fact 5 and criterion 13, seen again on staging on 2026-10-14; Q19), so before answering, the hook does R23's work: the loop stands down and the run's later writes are dropped as after `/terminate`, an outstanding run's result is written `failed` with the lost-VM reason (bounded), the report-server token is revoked (bounded at 10 seconds), and the status document is written `failed` with the reason (bounded), only while it records this VM. **The suspend-hook check** (REPORT-143 R1): an API `SuspendMicrovm` delivers `/suspend` (answered on staging, 2026-10-14), and the runner flushes and verifies before every `/idle` (R10, R11) all the same, so the data never depends on it. On a resume with no `/suspend` since the last activity the runner logs `lifecycle.resume_without_suspend`, which is the signal that the hook did not fire (Q5).
- **R23.** **`/terminate`**: if a package is running, its heartbeat is stopped (R44a) and its result is written `failed` with REPORT-143's one lost-VM reason, "The machine running it stopped before the run finished; run it again." (bounded, first, so it lands within the hook's 60 seconds whatever the flush costs); the report-server token is revoked (bounded at 10 seconds, a failure logged and ignored as today); the package's processes are stopped as R22 stops them, since this flush has no next scan to repair a file still being written; the syncer flushes and verifies (the lost-run write, the revocation and the stop are each bounded at 10 seconds, so in the worst case the flush has about 30 of the hook's 60 seconds); the status document is written `terminated`, or `failed` with the incomplete-sync reason (bounded), **in a transaction that writes only while the document's `microvm_id` is this VM's**, so a VM the researcher launched within the hook's 60 seconds keeps its document; a document naming another VM is left alone and logged as `terminate.runner_doc_skipped`. The write names the outstanding run in `current_package` (R8). The hook's failure is the run's last word: a package that finishes or fails after it writes no counts and no final result, since what it left after the hook's flush was never synced. The flush's verification still fails the hook. **An API `TerminateMicrovm` on an awake VM does not deliver this hook**: it arrives as `/suspend` and then termination, with no `/terminate` (staging, 2026-10-14, against AWS's lifecycle documentation and `design.md` criterion 11). R22's writes are then the VM's last, a proven flush writing `suspended` with `current_package` naming the run, and the lost-run write and the revocation fall to REPORT-143's lease (R17, with R19a writing the runner document `terminated`) and the token's nine-hour expiry. The handler stays, since AWS's documentation still describes it and whether the eight-hour cap delivers it to an awake VM is not known (Q20).
- **R24.** **`POST /refresh-token` and `POST /run-package` are deleted**, with their handlers, their tests, their mentions in comments, and the `refresh_token.*` and `analyze.*` log events. `GET /` stays for a human, reporting `state`, `microvm_id`, `current_package`, `expires_at` and the sync backend.

### The window, the ceiling and the timeout

- **R25.** **The window check runs twice.** Up front, for each adopted `/work` answer, once every package in it has been fetched and verified (R30): the declared durations of its packages are summed in order against the time left, which is the VM's eight hours from `/run` less 5 minutes for the last flush and the `/terminate` hook, and every package from the one the window runs out on is failed with "VM window exhausted: <n>s left, and this package and the ones before it declare <m>s". Then again before each claim: a package whose declared duration exceeds the time left is failed the same way, with the rest of that answer. Time left is read from the wall clock, which advances across a suspend (staging, 2026-10-15), and the watchdog fails a run the eight-hour cap cuts short (REPORT-143 R17).
- **R26.** **The ceiling.** A manifest declaring more than `PACKAGE_MAX_DURATION_SECONDS` is refused, written `failed` with the declared value and the ceiling. A manifest without a positive integer `expected_duration_seconds` is refused too. The default is 7,200, and a test asserts it equals the contract fixture's `limits.max_duration_seconds` (REPORT-167 R26). A configured value that is not an integer, is below that default or is above 28,800 stops the runner at startup with the reason, before it serves a hook, since a lower ceiling would refuse packages report-server accepts and a higher one would let a claim fail REPORT-143's rules. The value written onto a claimed result is the declared one, which is then at most the ceiling and at most 28,800. report-server refuses more than 7,200 at publish (REPORT-167 R21), so this check binds only on versions published before that.
- **R27.** **The in-VM timeout** bounds each package's process at its declared duration plus 10 minutes, the margin the watchdog uses, unless `PACKAGE_TIMEOUT_MS` overrides it, counted in the VM's awake time: the VM's clock runs on while it is suspended (staging, 2026-10-15), so `/suspend` pauses the bound and `/resume` arms it again with what was left, and a claim that lands while `/suspend` runs is armed when its package starts, after the resume. It is kept for a runaway on a VM that stays awake: a hung package keeps heartbeating (R44a), so REPORT-143's lease never ends it, and this timeout does. When it fires, the package uid's processes are killed (R28a's kill) and its step given up to 10 seconds to end before the failure is written, a canceled run writes no later stage, and the bound aborts the sandboxed process, which is killed with SIGKILL, so nothing of a timed-out package runs on into the next package's turn as the same uid. The lease, not this timeout, is the stall guard for a runner that stops (`final-design.md` 7.2).

### Running a package

- **R28.** **Every per-package path is keyed by the identity**, through its package key (the identity with `/` as `__`, a single path segment): the package's home `<workRoot>/home/<package_key>`, its input directory `<workRoot>/in/<package_key>`, its output directory `<workRoot>/out/<package_key>`, and the fetch cache `<workRoot>/packages/<package_key>/<version>.zip` with the archive unpacked beside it. The output directory is emptied before each run, so a package that writes no `display.md` cannot be credited with its last run's.
- **R28a.** `/work` and the directories under it that hold the per-package paths belong to the runner (root), and only the package's own home and output directory are handed to the package's uid, so a package cannot replace a directory the runner later reads as root. The runner reads `display.md`, `summary.txt` and `counts.json` without following a link: the output directory must resolve to itself, and each file must be a regular file opened with `O_NOFOLLOW` and `O_NONBLOCK`, so a named pipe left in a file's place is refused rather than blocking the runner's process. A link is refused, so a package cannot have root copy a file it could not read itself into its result. Likewise, the ownership walk that hands the class data directory and the cc-data root to the package's uid follows no link: a link there is skipped and every change of owner is an `lchown`, so a link left by one run cannot make the package the owner of the link's target at the next. A file with more than one hard link is neither handed over, read, nor synced to S3 (the syncer logs each such path once as `sync.unsyncable` and the verify names them, so the loss is visible), and the syncer, running as root over the package's tree, opens each file it uploads with `O_NOFOLLOW` and `O_NONBLOCK` and skips anything that is not a single-linked regular file at the path it scanned, so nothing swapped in after the scan is read or blocks a flush: `fs.protected_hardlinks` is not relied on, since whether the VM's root may set it is not recorded, and the two checks close both paths without it. Before reading, after every run whether it succeeded, failed or timed out, the runner kills every process the package uid owns (`kill -KILL -1` run as that uid) and repeats until `pgrep -u <uid> --runstates R,S,D,T,t` finds none (a killed orphan stays a zombie, unreaped while the runner's node is PID 1, and a zombie runs nothing), failing the package if five kills do not clear them or the check cannot run. A kill that fails there, or after a package past its bound, also stops the runner claiming: before each plan with packages in it the runner tries the kill again, and while it still fails every queued package is written refused ("The machine's last package could not be stopped, so nothing more runs on it; run it again."), so no package runs beside a survivor and `/idle` can still suspend the VM; the first kill that succeeds clears it. Every package runs as the same uid, so a process one left in the background could otherwise write the next one's output, or swap its output directory between the check and the read.
- **R29.** The result document id is the package key, derived by the runner from the identity. `/work`'s own `package_key` is not used, and the runner refuses a package whose `package_key` disagrees. The one exception is an identity that fails the grammar (R6): its refusal is written at `/work`'s `package_key` when that is itself a well-formed key, since nothing else addresses the result, and an entry with neither is logged and left.
- **R30.** The archive is fetched from `packages/<identity>/<version>.zip` (`PACKAGES_PREFIX` and a `packageKey(identity, version)` beside it, RD-4 pass 1 Q4), in both backends, and verified against the checksum `/work` handed out, which rigse took from the catalog. It is fetched and verified once per VM for an identity, version and checksum; later plans reuse the verified manifest and the unpacked copy, which sits under the root-owned work root (R28a).
- **R31.** The archive is unpacked only after the checksum passes, and its **actual** inflated size is bounded: the runner counts the bytes `unzip -p` produces and refuses the archive past 50 MiB (REPORT-142 R6's limit) before extracting anything. After extraction, an archive holding a symbolic link is refused and its directory removed, and every unpacked entry's mode is set to 0755 for a directory or an executable file and 0644 otherwise, since unzip restores the archive's modes and every package runs as one uid that could otherwise rewrite another package's cached code. No entry can land outside the package directory: Info-ZIP writes a `../` or absolute entry inside the destination (Stage 1 verification), so the runner does not check for one.
- **R32.** The manifest is read from the verified archive. Its `name` must equal the identity's last segment and its `version` the version handed out, or the package is refused. `entrypoint` must stay inside the package directory, as today.
- **R33.** A refused or failed fetch writes the result `failed` with the reason, never `running`, and goes on with the next package.

### Applicability

- **R34.** **The runner decides, report-server matches.** A manifest whose `urls` declares no pattern in any group applies to every class, and no call is made. Otherwise, before claiming, the runner reads the class's profile document `classes/{class_hash}` through that class's store and asks `POST <report_server_url>/api/v1/packages/applies` with its own report-server token as the bearer and the body `{urls: <the manifest's urls, as read from the verified archive>, scope_urls: <the profile's assignment_urls and interactive_urls together>}`, sending no `assignment_urls`, so nothing is derived and the answer matches the profile the app's list matched (REPORT-167 R15, R19). A yes is kept for that class, identity and version until the next resume, so a re-plan after each package (R7) does not ask again. `applies: false` writes the result `failed` with "the package does not apply to this class: <reason>", report-server's reason verbatim. A package that declares patterns on a class with no profile document is refused with "this class's authored profile has not been derived yet", without a call.
- **R35.** **What the runner makes of the other answers.** A profile that cannot be read, a 503, a 5xx, an answer without a boolean `applies`, a network failure, and no answer within 30 seconds each count as a failed claim attempt (R9), logged as `report_server.refused` with the status. The third one writes the result `failed` with "report-server could not say whether the package applies to this class (<reason>); run it again", so a report-server outage drains the queue and the VM can suspend, where a package left queued would hold it awake until its cap (R9, since `/idle` declines to suspend with work queued). A 400 or 422 is a refusal: the result is written `failed` with report-server's message, since it says the request is one report-server will never accept: publish already checks patterns with the applies route's rules, and the profile's URLs are within the route's bound, so a 400 means the runner and report-server disagree on the contract, which no retry fixes (Q18). A 401 or 403 means the runner's report-server token is no longer good, which nothing in the VM can fix: it is a failed claim attempt too, logged with the status. The runner never reads a 404 as "the route is not deployed"; it is a failed claim attempt like any other unexpected answer.
- **R36.** The runner holds no matcher and no copy of `fixtures/url-patterns.json`, which is report-server's test file (REPORT-167 R8). A test pins R34's request (the path, the bearer, the body's two keys and that `urls` is the manifest's as read from the archive) and R35's handling of each answer against a stub report-server.

### The documents

- **R42.** **One result per researcher per package per class**, at `researcher_dashboard/{portal}/classes/{class_hash}/researchers/{platform_user_id}/results/{package_key}`, written through that class's store. The shared `classes/{class_hash}/results/` is not written, and `requested_by` is gone.
- **R43.** A result claimed is written `status: "running"`, `stage: "starting"`, `package: {identity, version, checksum}`, `image_version`, `microvm_id`, `expected_duration_seconds`, `heartbeat_seconds: 60`, `started_at`, `finished_at: null`, `error: null`, `summary: null`, `display: null`. REPORT-143's rules refuse a `running` write without `heartbeat_seconds` (an integer 30 to 120), so a claim without it fails on every stack. A result refused before its claim is written `status: "failed"`, `error`, `finished_at`, `package`, and `stage`, `summary`, `display`, `image_version`, `microvm_id`, `expected_duration_seconds` and `heartbeat_seconds` as `null` (R44); the rules constrain the last four only on a `running` write. Stages are written as they begin: `prepare_package`, `run_package`.
- **R44.** A result finished is written in one call: `status: "done"`, `stage: "done"`, `package`, `image_version`, `summary`, `display`, `finished_at`, `error: null`. A run that fails is written `failed` with the redacted reason, `stage` left at the stage it failed in. **The runner's fields on a result describe only its latest run**: the claim clears the last run's `summary` and `display` (Q8), and a package refused before any claim is written `failed` with `summary`, `display`, `stage` and the last run's VM, image, declared duration and heartbeat interval cleared, since it never ran. report-service's re-queue already replaces the document with `previous` holding the last finished run, so this guards a document that still carries them (`started_at` stays: the rules refuse clearing it). `previous`, the last finished run that `/run-package` writes when it re-queues a package (REPORT-143 R8a), is not the runner's: every runner write to a result (the claim, a stage, a beat, the finish and a failure) merges named fields and never names `previous`, so it survives them all, and a test pins that it survives a claim, a finish and a failure.
- **R44a.** **The heartbeat** (REPORT-143 R17, Q13). From the claim until the run's final write, the runner merges `{platform_id, updated_at}` (server time) into the result every 60 seconds through the run's own class store. The interval and the claim's `heartbeat_seconds` are one constant, so they cannot disagree, and it is not configurable, since the rules bound it at 30 to 120. A beat is skipped while the previous one is unsettled, so a slow Firestore never stacks writes. Before the final write (`done`, or `failed`) the timer is stopped and any beat in flight is awaited, so no beat lands on a finished result and bumps its `updated_at`. A beat that fails is logged as `heartbeat.failed` and does not fail the run: the lease fails it only if beats stop for five minutes. The beat runs while the package does, including across a suspend and resume; REPORT-143's wake writes `resumed_at`, which restarts the lease.
- **R44b.** **A run's final write settles before anything else is written.** The run's final write, `done` or `failed` (a `failed` after a `done` the SDK rejected included), is awaited until the SDK's write promise resolves or rejects, never cut short by a local timeout, since a write the runner stopped waiting for can still land. Until it has settled, the run's class store stays open and the runner writes nothing else: no runner document write (R8), no other result and no next claim. A final write that never settles leaves the runner waiting with its heartbeat stopped, which the lease answers: the watchdog terminates the VM and fails the result. `/terminate`'s failure write is the exception, bounded like every hook write (R21, R23), since the hook has 60 seconds and the VM ends after it; the runner-document write that follows it names the run in `current_package` (R8), so REPORT-143's moved-on case cannot read it as the runner having moved on.
- **R45.** Every runner write to a result or to `runners/` carries `platform_id` and sets `updated_at` to server time, and every other timestamp the runner writes to Firestore (`started_at`, `finished_at`, `last_pull_at`) is server time too, since no clock inside the VM is real after a suspend. The one exception is the status document's `expires_at`, computed at `/run` from a VM that has just booted.
- **R46.** **The counts** are written after each successful run onto `classes/{class_hash}/researchers/{platform_user_id}`: `platform_id` and `data: {answers, logs, last_pull_at, log_freshness_at}`, with `last_pull_at` server time, and `log_freshness_at` the package's value as a Firestore timestamp when it parses as a date, and absent otherwise. The write replaces `data` as a whole: a count the package did not write is absent, never left over from an earlier run of another package, since a merge keeps the old value beside the new ones (Q17). So any of `answers`, `logs` and `log_freshness_at` can be absent, which RD-3 renders as not reported, and `last_pull_at` is always present. Nothing is written to `classes/{class_hash}`.
- **R46a.** The status document's `scopes` replaces `classes`: the class hashes the synced tree holds data for, plus the one being run.

## Technical Notes

- **What only a real VM could show**, answered on staging on the QA stack (the stream's `rd4-pass2-staging-checks.md`):
  - `/run`'s body carries `microvmId`, and every log line carries it, equal to `vms/`'s and the result's (2026-10-14).
  - An API `SuspendMicrovm` delivers `/suspend` (REPORT-143 R1; 2026-10-14, three times), and no `lifecycle.resume_without_suspend` followed.
  - The Firebase refresh token still yields an ID token after a suspend longer than an hour: an idle VM resumed after 61 minutes took new work (2026-10-14), and a run's class store kept writing after a 65-minute mid-run suspend (2026-10-15).
  - The VM's clock, Node's timers included, advances across a suspend (2026-10-15), which is why R27 counts awake time.
  - An API `TerminateMicrovm` on an awake VM delivers `/suspend`, then terminates, never `/terminate` (2026-10-14, R23, Q20); a `/suspend` answering 500 is followed by termination with no `/terminate` (Q19).
  - Nothing in the image makes an AWS call of its own: the log shows `aws.default_chain_disabled`, broker credentials and no `CredentialsProviderError`, and the isolation probe found IMDS, the container-credentials endpoint and every S3 read unreachable from a package (2026-10-15).
- **A profile URL is always within report-server's bound.** The function bounds a profile URL at 2,048 UTF-16 code units (`derive-profile.ts` line 207, `derive-profile-route.ts` line 42), and REPORT-167 bounds a scope URL at 2,048 code points, which a URL never has more of; REPORT-167 aligned it after this spec found a byte bound would refuse a non-ASCII URL near the limit.
- **The watchdog's `terminated` write and the runner.** The watchdog writes `runners/{uid}` `terminated` only for a VM that is gone, and only while the document names that VM and is not already terminal (REPORT-143 R17, R19a), so the runner that wrote the document last never runs again to see it, and a newer VM's document is never touched. R8's write-once `ready` is unaffected.
- **The fixture's `limits` and the runner's.** `limits.max_duration_seconds` is R26's default. `limits.max_url_length` is report-server's and the function's; the runner sends the profile's URLs as stored and lets report-server judge them (R35), so it keeps no copy of that number.
- **The watchdog's view of a running package.** The heartbeat (R44a) is the only proof of life REPORT-143's lease reads. A runner that stops beating, through a crash, a hung event loop or a final write that never settles, has its VM terminated and its result failed within about 7 to 9 minutes. A package that hangs while the runner beats is bounded only by R27's timeout.
- **Why the moved-on case cannot fail a live run.** REPORT-143 fails a stale result without a kill when the runner document names the same VM, is not terminal, names another `current_package` and was written after the result. Only two runner writes change `current_package`: the next claim's and the drained `ready` (R8), and both wait for the last run's final write to settle (R44b). The hooks write the outstanding run's own `current_package`, and leave the field alone when none is outstanding. So a document naming another package means the earlier run's last write has already resolved or been refused, and nothing will write that result again.
- **Ordering within one store.** The beat, the final write and `/terminate`'s failure all go through the run's class store, and the Firestore SDK sends one instance's writes in the order they were made. So `/terminate` stops the beat's timer and writes the failure without waiting for a beat in flight, which would spend the hook's 60 seconds on a write that lands first anyway.
- **`microvm_id`'s form is checked by `/work`.** REPORT-143 compares the runner's `microvm_id` with `vms/`'s, which holds `RunMicrovm`'s id, in R17's same-VM tests and R19a's guard. The runner writes `/run`'s `microvmId` unchanged (R1, R8, R43), and `/work` answers 409 to any id that differs from `vms/`'s by exact string comparison (REPORT-143 R6a, `vm-routes.ts`), so a runner that has claimed anything has already shown that the two forms agree. A differing form would show as a VM that never takes work, a 409 on every `/work` after its first minute.
- **The runner's VM is not relaunched when its window runs out.** REPORT-141's function reuses a `RUNNING` VM whatever its age, so a package failed with "VM window exhausted" and run again lands on the same VM until it reaches its cap. That is the function's behavior and is recorded for REPORT-143's follow-up, not changed here.
- **`STATUS_BACKEND` is `FIRESTORE` or `MEMORY`.** Every call to the function needs the session's ID token, so a store that signs nothing in could never pass `/run`'s claims check (R3); `LOG` is refused at startup. RD-1 fixes `STATUS_BACKEND=FIRESTORE` on the image.
- **`RD_DATA_DIR` is shared by every package of a class.** The per-package paths of R28 are the runner's; the class's data directory stays shared, since it holds the researcher's pulled corpus. A package that keeps state there under a file name it chooses (the spike's `_lib` wrote `runs.json`) can collide with another package's, so REPORT-147's packages keep their state in their own dataset (`pkg-<catalog id>`, R39).
- **`/run` stays inside 60 seconds** with one more upstream call (the credentials, bounded at 15 seconds). The spike measured `/run` at 4.5 seconds with a two-second pull-down (`design.md`, criterion measurements); a large prefix's pull-down is the risk it already was.
- **A runner token cannot write the scope document's timestamp as server time only by rule.** REPORT-143's rules require server time on `runners/` and results, not on `classes/{h}/researchers/{uid}`; R45 applies it there too, by choice.

## Decisions

### Requirements

- **Polling while idle (Q1, R10).** `/work` every 30 seconds through a 5-minute idle period, then `/idle`, over no polling (work requested on a warm VM waits the whole period) and a listener on the runner document (a long-lived listener on a per-request store, whose token goes stale on the SDK's timer). Both numbers are code defaults with environment overrides.
- **`publish-package.sh` deleted (Q4, R55).** `/work` hands out only what rigse resolved against report-server's catalog, so an object the script uploads can never be queued; publishing goes through report-server.
- **The suspend path (Q5, R22).** Assume `/suspend` fires, and flush and verify before every `/idle` anyway, so a suspend with no hook loses no data; `lifecycle.resume_without_suspend` shows a missing hook in the log. Staging later showed the hook fires.
- **Metrics as log lines only (Q6, R50).** Stable event names a log-based metric can count later; no alarm exists to read a metric, and RD-1's execution role holds no `PutMetricData`.
- **The duration ceiling is 7,200 seconds (Q7, R26).** At 28,800 one package could claim a fresh VM's whole life. REPORT-167 adopted 7,200 as report-server's publish limit and the contract fixture's, so the number has one home outside this repository.
- **A claim clears the last run's display (Q8, R44).** A result is only ever its latest run; keeping a stale display beside a newer version is `final-design.md` 8's attribution defect. `previous` is the function's and survives every runner write.
- **`requested_at` is REPORT-141's `queued_at` (Q9).** The runner writes `started_at` and `finished_at`, and no `requested_at`.
- **Counts through `counts.json` (Q10, R41a).** Reading `answers`, `logs` and `log_freshness_at` only, over the runner querying the package's dataset itself (coupling the runner to cc-data's queries) or dropping the counts.
- **The smoke package is published `official` with narrow patterns (Q11, R53; Doug, 2026-09-26).** Over turning on report-server's unreviewed runs or waiting for REPORT-147. Its class is staging class 590, whose one assignment is assigned nowhere else; class 223's are shared with five other classes.
- **`scope.json`'s `dataset` is the bare name (Q13, R39).** What `cc-data package run` writes and REPORT-147 encodes; packages read `RD_DATASET`, the full ref.
- **The contract fixture is a byte-identical copy (Q14, R6; Doug, 2026-10-08).** `runner/scripts/contract.mjs` fetches report-service's file from GitHub (`contract:sync`) and fails on drift (`contract:check`), run at each release and monthly rebuild. A report-server endpoint would have meant moving the file into its image; a test reading GitHub would make `npm test` depend on the network.
- **The smoke package stays the release gate (Q15; Doug, 2026-10-08).** It needs no Wildfire class and gates every later release.
- **The applies call sends the profile's URLs as `scope_urls` (Q16, R34).** One read the runner already makes, a fast answer, and the same set the app's list matched, over the scope block's `assignment_urls`, which can wait minutes on a deriver and differ from the app's answer.
- **The counts replace `data` whole (Q17, R46).** A merge would mix counts from different packages and runs; so a count the package did not write is absent, and only `last_pull_at` is always present.
- **A 400 or 422 from the applies route is a refusal (Q18, R35).** Publish checks patterns with the same rules and profile URLs are within the route's bound, so a 400 means the two sides disagree on the contract, which no retry fixes.
- **A refused `/suspend` does `/terminate`'s work, and `/suspend` freezes the package first (Q19, R22; Doug, 2026-10-15).** Lambda terminates a VM whose `/suspend` answers 500, with no `/terminate`, so the runner fails the run and revokes its token before answering; stopping the package's processes keeps a package still writing from failing the verify.
- **An API terminate that delivers only `/suspend` is recorded, not handled (Q20, R23; Doug, 2026-10-15).** Moving the lost-run write into `/suspend` would fail runs a real suspend only pauses; the lease and the token's expiry cover it. R19a's `failed` left on a dead VM's runner document stays.
- **A run's bound counts awake time, and the post-resume cycle writes `running` (Q21, R20, R27; Doug, 2026-10-15).** `/suspend` pauses the bound and `/resume` re-arms it with what was left; `/resume` itself still writes nothing.
- **Q2, Q3 and Q12 (CLUE's project, an expired CLUE token, CLUE-692's deploy) were superseded** by deleting the CLUE pre-pull (R56a).
- **A class store a running package writes through is kept** past the next adoption until its final write settles (R4), since a write through a deleted app fails.
- **The window is eight hours from `/run` less 5 minutes** for the last flush and `/terminate`, checked once every package in the answer is fetched (R25).
- **The pre-`/idle` flush runs immediately before each `/idle` call** (R10), not when the queue drains.
- **Recorded status-write failures are redacted** before they reach the status document (R21), which the researcher's browser reads.
- **`STATUS_BACKEND=LOG` is refused at startup**: a store that signs nothing in can never pass `/run`'s claims check.
- **An unwritable claim is tried three times per awake period** (R9), then written refused so `/idle` can suspend the VM; the count clears once the entry is claimed or written refused, and on every resume.
- **`log_freshness_at` is converted to a Firestore timestamp** when it parses, and dropped when it does not (R46).
- **Package state belongs in the package's own dataset**, since `RD_DATA_DIR` is shared by every package of a class.
- **The ten-hour Done-when sentence is checked by tests only**: report-server refuses more than 7,200 seconds at publish, so no such version can reach a staging VM.
- **The cc-data pin waits for its tag** (R60): the release runs from the branch and needs the tag, so `main` never names a ref that cannot be built (Doug's rule that infrastructure rolls out before merge).
- **While a run is outstanding, every runner-document write names it in `current_package`** (R8; Doug, 2026-10-14), so a lost claim-time write is repaired by the next hook write and REPORT-143's moved-on case cannot fail a run suspended mid-run.
- **The runner keeps no portal row** (R56): with the CLUE lookup gone, nothing read it.

### Implementation

- **`MemoryStore.merge` merges nested maps as Firestore does**, so the default suite can fail on a write Firestore would merge; the emulator suite is skipped where the emulators are absent.
- **The applies call is bounded at 30 seconds**: report-server derives nothing for `scope_urls`, and a slow answer is a failed claim attempt, not a refusal.
- **Local paths are keyed by the package key**, one segment, the result document's id, needing no permissions on intermediate directories; the S3 key keeps the identity's slashes.
- **`/work` is asked again after every package**, so work appended meanwhile is seen and each package writes with fresh tokens; verified manifests (for the VM's life) and report-server's yes (until the next resume) are kept, so re-planning fetches and asks nothing twice.
- **A failed counts write does not fail the run**: it is logged as `status.write_failed`, and the next run rewrites the counts.
- **The smoke package's patterns are set at build time** (`--any`), since the smoke class differs by stack.
- **Root reads a package's output without following links** (R28a): `/work` stays root's, and `readOwnFile` refuses a swapped directory and opens each file with `O_NOFOLLOW` and `O_NONBLOCK`.
- **A drained VM writes `ready` once**, not on every idle poll; a late launch record is corrected by the first `/work` the loop takes.
- **A test that mocks timers enables them before the run starts**, so the run's bound is a mocked timer the test can end, and `npm test` exits on its own.
- **A report-server outage fails the package after three failed applies checks** with a run-it-again reason (R35), so the VM can suspend rather than poll until its cap.
- **Epoch checks after the pre-`/idle` flush and between planning and running** (R12), so a loop stood down by a resume never calls `/idle` under the new loop's package.
- **The status document's `queue` leaves out entries the same plan wrote `failed`** (R8).
- **Every process of the package uid is killed after each run** (R28a; Doug, 2026-10-08), repeated until `pgrep` finds none, over a PID namespace per package, which failed open on a SIGTERM timeout.
- **A push workflow runs the tests; the monthly rebuild is manual** (R54, R54b; Doug, 2026-10-08): a scheduled job was judged over-engineering.
- **`/run` logs the default chain's state** from the process's environment (R16), since the switch itself runs at image build.
- **`make run-hook` is deleted** (R54a; Doug, 2026-10-08): making it work would still run no package, and its DIR-mode `cc-data login` replaced the developer's own credential.
- **The revocation is bounded at 10 seconds** (`REVOKE_TIMEOUT_MS`).
- **The freeze's races are closed in the runner, not left to the watchdog** (Doug, 2026-10-15, after the final review): a claim landing during `/suspend` waits for the resume, the continue waits for a stop still under way, and a loop stands down once the VM is ending, so a stray `/resume` claims nothing.
- **`/terminate` tolerates a run whose heartbeat has not started** (`heartbeat?.cancel()`), and both of its runner-document writes take the `microvm_id` guard.
- **The Makefile reads `VERSION` from `package.json` with `sed`** and stops on an empty value, since Node is not on every shell's `PATH`.
- **`smoke.mjs` gained `build --version`, `build --hold` and `stack --wait-minutes`**, since report-server refuses a version it already holds and the long-run checks outlast a 10-minute wait.
- **Logs pinned by tests** (S8-Q1, S8-Q3): a run's lines carry the researcher, VM, scope and package and lose the last two after it; the five event names fire on their triggers, `report_server.refused` on both calls with `call` set.
- **The smoke gate has make targets** (S8-Q2, R54a), which the monthly rebuild calls.
